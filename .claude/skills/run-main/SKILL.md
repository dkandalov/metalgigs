---
name: run-main
description: Run the app's main entry point to scrape gigs, classify their genre, manually override a gig's genre, ingest a poster-only venue's gigs from an image, render the HTML page (which also reports unresolved gigs), prune orphaned cached images, or all of scrape+classify+render. Use when asked to run the app, scrape gigs, classify gigs, list/review unresolved gigs, override/correct a gig's genre, ingest a gig poster image, clean up stale cached images, or render the gigs page.
---

Run `.claude/scripts/run-main.sh [scrape [venue-key...] [force]|classify [limit]|override <url> <metal|other>|render [yyyy-mm-dd] [force] [full-unresolved]|prune-images|ingest-poster <imageUrl> <sourceUrl> <venue> [force]|all]` from the project root using the Bash tool. Two calling conventions, and they behave differently — pick based on whether any argument needs a literal space in it:
  - **Separate arguments** (`.claude/scripts/run-main.sh "ingest-poster" "https://.../poster.jpg" "https://.../post" "The Dev"`, one Bash-tool string per logical argument): each argument's own spaces survive intact. Use this whenever an argument itself needs to contain a space, e.g. `ingest-poster`'s free-text `venue`, or a url that happens to have one.
  - **One combined string** (`.claude/scripts/run-main.sh "classify 5"`, `.claude/scripts/run-main.sh "render force"`): gets split into separate arguments on whitespace, so don't use this form for anything containing a value that must keep its spaces — e.g. `ingest-poster "https://.../poster.jpg" "https://.../post" "The Dev"` as one combined string would wrongly split "The Dev" into two arguments and miscount `ingest-poster`'s 3 required positional args.
  (Mechanically: the script encodes and joins separate arguments itself before handing them to `gradlew run --args=...`, since Gradle's `--args` value is otherwise re-split on any whitespace before Kotlin ever sees it, which is also why a single combined string works the same as before — Gradle does that splitting itself in that case.)

Genre is judged by one classifier (the LLM), but sampled twice per gig, and confidence comes from whether those samples agree. Agreement means the model is consistent about that gig and its verdict stands (`ClassificationStatus.Classified(genre)`); disagreement means it isn't, and the gig becomes `NeedsReview` for a human to settle rather than trusting either answer. A gig no classifier has touched yet is `Pending`. Both `NeedsReview` and `Pending` stay out of the rendered Metal page. A `source = User` override (via `override`) is always final and beats anything the classifier said. Sampling only means something at a non-zero temperature — at temperature 0 the two replies would be near-identical by construction and always "agree", measuring nothing.

- `scrape [venue-key...] [force]` fetches gigs and appends a `GigObserved` entry per gig to `events.ndjson` (the append-only event log; never overwritten) — but first skips any venue scraped within the last day, printing "Skipping <venue> - scraped within the last day; pass force to scrape anyway" for each one and leaving it untouched. "Scraped within the last day" is approximated from the latest `GigObserved` per venue, not a dedicated scrape-event record, so a venue with no changes for longer than a day looks stale and gets rescraped anyway - that's the safe direction to be wrong in (scraped a bit more often than strictly necessary, never less). Pass `force` to bypass the cooldown and scrape every requested venue regardless. With no venue keys, considers all fifteen venues (skipping/scraping each per the cooldown); with one or more keys (e.g. `scrape dome underworld`), only those. Known keys: `cart-and-horses`, `new-cross-inn`, `our-black-heart`, `underworld`, `dome`, `blondies-taproom`, `blondies-bar`, `helgis`, `electric-ballroom`, `dingwalls`, `the-garage`, `roundhouse`, `signature-brew-blackhorse-road`, `signature-brew-haggerston`, `o2-forum-kentish-town`. An unknown key fails fast with the list of valid keys. `o2-forum-kentish-town`'s listing page renders client-side and paginates in the browser, so unlike the other venues it doesn't scrape HTML at all — it calls the JSON API that page feeds itself from (`/api/search/events?VenueIds=5597&...`), with a `PageSize` well above the number of events actually listed so everything arrives in one request rather than needing to page through. The two Signature Brew keys share one page (`events.signaturebrew.co.uk`) that lists both taprooms' gigs together, each tagged with its own venue name — each key fetches that same page independently and filters to its own venue, so scraping both in one run means two requests for identical content (a deliberate, minor tradeoff over adding a fetch-cache for one venue pair).
- `classify [limit]` projects the current gigs from `events.ndjson` and, for any gig not yet classified at all, fetches its event page and asks Claude Haiku (via `http4k-ai-llm-anthropic`) for a Metal/Other judgement — **twice**, sequentially, at temperature 1, recording both replies in the entry's `sampledGenres`. Requires an `ANTHROPIC_API_KEY` environment variable (fails fast with a clear message if missing) and makes two real paid API calls per gig, so the whole backlog is slow and worth chunking with the numeric `limit` (e.g. `classify 5` takes the next 5 soonest-upcoming unclassified gigs). Gigs already classified are skipped — **including ones needing review**: the samples already disagreed once, so re-running the same classifier would just as likely disagree again; it's waiting on a person, not on a retry. When an event page's text is too thin to judge (under 80 chars) and the gig has a poster image, it falls back to sending that image to Claude Sonnet instead (which rejects a temperature override, so it runs at the API's own non-zero default and still varies between samples). Poster images are cached only for gigs that become Metal as a result of this run. Prints a summary: how many gigs were classified, how many had agreeing vs disagreeing samples, and the overall current-gigs breakdown (Metal/Other/Pending/Needs review) across the whole log.
- `override <url> <metal|other>` appends a `GigClassified` entry with `source = User` for the gig with that url, asserting its genre directly and finally — it always wins regardless of what the classifier said or will say (including overriding a gig that needs review, which is the intended way to settle one), and a later `classify` run skips it. No network calls.
- `render [yyyy-mm-dd] [force] [full-unresolved]` first checks every current gig on or after the reference date (today by default, or the given `yyyy-mm-dd`) for unresolved classification — `Pending` or `NeedsReview` — sorted soonest-first. If any are found and `force` wasn't passed, it fails fast (writing nothing) with the count and, by default, just the soonest 5; each is listed as three lines: date/venue/title, then **why it's unresolved** ("Pending (not yet classified)", or "Needs review (LLM sampled Metal/Other)" showing what the samples were torn between), then its url. Pass `full-unresolved` to list all of them instead of just 5 (there is no standalone command for this — `render` without `force` doubles as the "what's left to classify" report, and is the only way to see the full list). Pass `force` to skip the check and render anyway. Once past the check (or with `force`), it keeps only the gigs settled as Metal (settled-`Other` gigs are excluded too), excludes gigs before the reference date, and writes `index.html` (no network calls). Only settled-Metal gigs are guaranteed to have a cached poster image (see `classify`/`override`), so this filtering isn't optional — anything else would risk broken `<img>` tags. `all` calls `render` without `force`, so it fails the same way if an upcoming gig is still unresolved after `classify` runs — this is deliberate (see `all` below).
- `prune-images` deletes any file under `images/` that doesn't match a currently settled-Metal gig's expected filename (computed with the same `localImageFileName` hash used to write them) — e.g. leftovers from a gig later overridden away from Metal, or from before caching became Metal-only. Prints each removed filename and a trailing count. No network calls; safe to re-run (reports 0 removed once caught up).
- `ingest-poster <imageUrl> <sourceUrl> <venue> [force]` is for a venue whose gigs are never scrapeable normally — e.g. a monthly calendar posted only as a single flyer image on social media, where there's no page of per-gig markup to parse. It fetches `imageUrl` directly (not `sourceUrl` — that's never fetched, since e.g. Facebook blocks plain HTTP access to its pages outright; `imageUrl` needs to be the poster's own direct image link, obtained by the caller some other way, such as "copy image address" in a logged-in browser) and sends it to Claude Sonnet (vision) with a structured-extraction prompt asking for every gig's date and title. Every extracted gig gets `genre = Metal, source = User` immediately — there's no per-gig page text to classify against, so this assumes the whole poster is metal rather than leaving gigs `Pending` — and since there's no per-gig page to link to either, each gig's url is synthesized as `{sourceUrl}#gig-{slug(title)}-{date}`: a real, working link to the actual poster (sourceUrl), just not scrolled/highlighted to that one gig, since the source doesn't support that. Idempotent by default — skips (printing why) if any gig with this `sourceUrl`'s prefix is already in the log; pass `force` to re-run extraction anyway. Re-running is inherently a bit risky since the LLM re-reads the image fresh each time: if its wording of a title drifts slightly between runs, the derived url changes too, and it'll look like a new gig rather than an update — `force` should be used sparingly, not as a routine refresh.
- `all` (also the default when no argument is given) runs `scrape`, then `classify`, then `render` — it does not include `unclassified`, `override`, or `prune-images`, which are standalone. `scrape` here is not forced either, so running `all` again soon after skips any venue already scraped within the last day rather than re-hitting it. Since `classify` now always needs `ANTHROPIC_API_KEY`, so does `all`. `render` here is not forced, so if any upcoming gig is still `Pending`/`NeedsReview` after `classify` runs (a gig needing review can't be resolved by `classify` at all — re-running the classifier that already contradicted itself is not what it's waiting for), `all` fails at the render step rather than silently publishing a page with a gap — resolve it with `override` (or the `classify-unclassified-gigs` skill) and re-run.

Report what was produced and surface any errors from the Gradle output.
