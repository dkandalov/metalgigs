---
name: run-main
description: Run the app's main entry point to do the full daily update (scrape, classify, render), or any one step on its own - scrape gigs, classify their genre, manually override a gig's genre, ingest a poster-only venue's gigs from an image, or render the HTML page (which also reports unclassified gigs and keeps the cached images in sync). Use when asked to run the app, do a daily/full update or refresh, scrape gigs, classify gigs, list/review unclassified gigs, override/correct a gig's genre, ingest a gig poster image, clean up stale cached images, or render the gigs page.
---

Run `.claude/scripts/run-main.sh [daily-update [force]|scrape [venue-id...] [force]|classify [limit]|classify status|classify override <url> <metal|other>|render [yyyy-mm-dd] [force] [full-unresolved]|ingest-poster <imageUrl> <sourceUrl> <venue-id> [force]|compact]` from the project root using the Bash tool. There is no default — running it with no arguments, or an unrecognised one, just prints the usage line. For a full refresh use `daily-update` rather than chaining the three commands by hand. Two calling conventions, and they behave differently — pick based on whether any argument needs a literal space in it:
  - **Separate arguments** (`.claude/scripts/run-main.sh "ingest-poster" "https://.../poster.jpg" "https://.../post" "The Dev"`, one Bash-tool string per logical argument): each argument's own spaces survive intact. Use this whenever an argument itself needs to contain a space, e.g. `ingest-poster`'s free-text `venue`, or a url that happens to have one.
  - **One combined string** (`.claude/scripts/run-main.sh "classify 5"`, `.claude/scripts/run-main.sh "render force"`): gets split into separate arguments on whitespace, so don't use this form for anything containing a value that must keep its spaces — e.g. `ingest-poster "https://.../poster.jpg" "https://.../post" "The Dev"` as one combined string would wrongly split "The Dev" into two arguments and miscount `ingest-poster`'s 3 required positional args.
  (Mechanically: the script encodes and joins separate arguments itself before handing them to `gradlew run --args=...`, since Gradle's `--args` value is otherwise re-split on any whitespace before Kotlin ever sees it, which is also why a single combined string works the same as before — Gradle does that splitting itself in that case.)

For a standalone build, `./gradlew shadowJar` produces `build/libs/metalgigs.jar` (~10MB, all dependencies inside), run as `java -jar build/libs/metalgigs.jar <same arguments>` — no encoding needed, arguments pass through normally, unlike `run-main.sh`. It must be run **from the project root**: every path the app touches (`events.ndjson`, `images/`, `index.html`, `.image-cache/`, `.rendered/`) is relative to the working directory, so the jar is self-contained in dependencies but not in data. It also needs a **Java 21** runtime, matching `jvmToolchain(21)`: on Java 26 the TLS handshake for venues whose sites omit their intermediate CA cert (e.g. The Garage) fails with `PKIX path building failed` even with `-Dcom.sun.security.enableAIAcaIssuers=true`, whereas on 21 it succeeds. `main()` sets that property itself, so the jar needs no `-D` flag of its own.

Scrape captures each gig's description from its own event page and stores it on the gig (`Gig.description`), so classifying later needs no network and can't be defeated by a page that has since changed or gone. It's blank when the page couldn't be read, and the classifier fetches at classification time for those. Scrape deliberately does not re-observe a gig just to retry a blank description — that would log the same unchanged listing on every run — and `newOrChangedGigs` ignores the description when deciding whether a gig changed: it comes from a different page than the listing, and it churns, since re-reading every gig's page minutes apart changed one (a counter ticking over) and flipped eight from empty to full (a flaky JS-rendered site).

Images live in two places. `.image-cache/` (gitignored) is a download cache keyed by image url, holding **every** scraped gig's image whatever its genre — it's filled during `scrape`, while the urls are still fresh, because some expire (the Facebook CDN ones carry an expiry parameter) and waiting until a gig is classified and rendered can be too late. Keying by url also means one poster shared by a month of gigs is stored once. `images/` (committed) holds only what the rendered page references, produced from the cache by `render`. That split is what makes `render` safe to prune: republishing reads the cache, never re-fetching against a url that may since have died.

Publishing **re-encodes rather than copies**, so `render` needs **ImageMagick** on the machine (`magick` on `PATH`, or `MAGICK_BINARY` pointing at it). Each image is resized so its *shorter* side is at most 768px — the side that survives the square `object-fit: cover` crop, and 2x the 260px the cards actually render at — then written as webp at quality 80, metadata stripped. Images already smaller than 768px are left at their own size rather than upscaled. This took the committed set from 175MB to 18MB with no visible change at card size. Two things to know: ImageMagick treats **quality 100 as *lossless* webp** (about 5.6x larger than 80), so that number is not a quality dial to nudge upward; and every published file is named `.webp` regardless of source format, with the name saying nothing about the size or quality used — so changing either in `ImageMagick.kt` will *not* re-encode what's already in `images/`. Delete the directory and re-render to force that, which costs no network because the cache still holds the originals. A conversion that fails is reported per-gig and doesn't abort the render. The same 768px conversion is reused when `classify` falls back to the poster image: Claude bills an image at `ceil(w/28) * ceil(h/28)` visual tokens, so sending a venue original (1667px at The Underworld, 4385px at the dice.fm venues) costs 3600-4784 tokens against 784 for the rendition the page already shows, for detail a genre judgement never uses. `ingest-poster` deliberately keeps the full-size image, since it has to read dates and titles off the flyer.

Genre is judged by a single LLM call per gig, at temperature 0 so verdicts are reproducible. A gig with a classification is `ClassificationStatus.Classified(genre)`; one the classifier hasn't reached yet is `Pending` and stays out of the rendered Metal page. A `source = User` override (via `classify override`) is always final and beats the classifier's verdict.

- `daily-update [force]` runs `scrape`, then `classify`, then `render`, each printing under a `== step ==` header. It's the routine refresh, and the order is the only one that works: classifying can't judge gigs a scrape hasn't recorded yet, and rendering before classifying would leave them off the page. Each step calls the same function its own command does, so nothing behaves differently from running the three by hand. It runs **at most once a day**: if the log already holds a `GigsRendered` entry whose `logicalDate` is today it prints "Skipping - already updated for <date>; pass force to update anyway" and does nothing. The check is on `logicalDate`, not the newest render's timestamp, so a backdated `render <past date>` doesn't count as having done today, and today's counts however early in the day it happened. The log is the only state involved — nothing else tracks when the last update ran. `force` means "do it again anyway" and carries through to `scrape`, since that command's own per-venue cooldown would otherwise skip every venue and leave a forced run with nothing to do but re-render. It deliberately does **not** carry through to `render`, whose `force` means the unrelated "publish despite gigs nobody has classified" — never something a routine update should decide by itself; run `render force` yourself if that's what you want. Because each step persists as it goes (the log is append-only), a failure at `render` keeps everything `scrape` and `classify` just did — rerunning after settling those gigs costs only the render. Expect it to take a while: `classify` makes one paid API call per unclassified gig, so a run picking up a day's worth of new gigs can take several minutes, and one clearing a large backlog considerably longer.
- `scrape [venue-id...] [force]` fetches gigs and appends a `GigObserved` entry per gig to `events.ndjson` (the append-only event log; never overwritten), downloads every scraped gig's image into `.image-cache/`, and captures each gig's own event-page text onto the gig — but first skips any venue scraped within the last day, printing "Skipping <venue> - scraped within the last day; pass force to scrape anyway" for each one and leaving it untouched. After validating what it read, it also asks what became of each still-upcoming gig the log holds that the venue has stopped listing - one request to the old url, since only the run that first misses it can tell. A venue that redirects that url to a gig now listed has said where the gig went; one that has deleted the page (404/410) leaves the gig on that night whose title shares most of its words to stand in for saying so, and a page still being served says the gig has not moved at all. Either way of moving appends a `GigReplaced` entry, which is what stops a venue swapping a support act (Cart and Horses and dice.fm both build a url out of the title) from publishing one night as two cards: `currentGigs` leaves out a url that has been replaced, and `classificationStatus` reads the new url's genre from the old one, so the move costs neither a duplicate nor a paid call. Skipped for a venue whose gigs validation withheld, since a listing that failed a check is not one to conclude anything from. "Scraped within the last day" is approximated from the latest `GigObserved` per venue, not a dedicated scrape-event record, so a venue with no changes for longer than a day looks stale and gets rescraped anyway - that's the safe direction to be wrong in (scraped a bit more often than strictly necessary, never less). Pass `force` to bypass the cooldown and scrape every requested venue regardless. With no venue ids, considers all thirty-three venues (skipping/scraping each per the cooldown); with one or more ids (e.g. `scrape dome underworld`), only those. Known ids: `cart-and-horses`, `new-cross-inn`, `black-heart`, `underworld`, `dome`, `fiddlers-elbow`, `blondies-taproom`, `blondies-bar`, `helgis`, `electric-ballroom`, `electric-brixton`, `dingwalls`, `the-garage`, `roundhouse`, `signature-brew-blackhorse-road`, `signature-brew-haggerston`, `o2-forum-kentish-town`, `o2-academy-brixton`, `the-grace`, `o2-academy-islington`, `o2-shepherds-bush-empire`, `union-chapel`, `scala`, `229`, `alexandra-palace`, `paper-dress-vintage`, `windmill-brixton`, `islington-assembly-hall`, `barfly`, `eventim-apollo`, `ovo-arena`, `indigo-at-the-o2`, `the-o2-arena`. These are the `VenueId`s of the venues in `allVenues` that have a `GigsSource`; an unknown id fails fast with the list of valid ones. The Academy Music Group venues (`o2-forum-kentish-town`, `o2-academy-brixton`, `o2-academy-islington`, `o2-shepherds-bush-empire`) have listing pages that render client-side and paginate in the browser, so unlike the other venues they don't scrape HTML at all — they call the JSON API those pages feed themselves from (`/api/search/events?VenueIds=<ids>&...`), with a `PageSize` well above the number of events actually listed so everything arrives in one request rather than needing to page through. Adding another AMG venue only needs its numeric id, which appears in each event's own `venue` object in that same API response (calling the API with no `VenueIds` at all returns every venue's events, which is the easy way to look one up). A venue can need more than one id: `o2-academy-islington` passes `4361,4258` because its listing covers both the main room and the smaller "Academy2" upstairs, which has no listing page of its own — both are recorded under the one venue name, exactly as the site presents them. Their gigs are identified by ticket-vendor url (mostly Ticketmaster, occasionally another vendor), and any event whose ticket sales have already closed comes back with no tickets at all — those are skipped with a printed note, since they'd have neither a stable identity nor a working link. `new-cross-inn`'s page opens on the current month and its "Upcoming Months" dropdown doesn't navigate — it POSTs to WordPress's `admin-ajax.php` (`action=nci_monthly_events_results`, `month`, `year`) and swaps the listing in place, so every later month is only reachable through that call and the scraper follows the dropdown's own list of months. That POST needs an explicit `content-type: application/x-www-form-urlencoded`: http4k's `form()` sets the body but not the header, and admin-ajax fills `$_POST` from that header alone — without it the action never arrives and WordPress answers 400 rather than erroring in any way that names the cause. Its gigs' descriptions come from pit.live, which renders them client-side: the copy is a JavaScript string literal in an `x-html` attribute, with angle brackets and ampersands written as unicode escapes, so it's decoded through the JSON parser (every escape it uses is one JSON has) and then parsed again as the HTML it turns out to be. Taken raw it reaches the classifier as escapes and tags rather than prose. The page's own meta description is no substitute — it's "Buy tickets for X live at Y", identical on every listing. `black-heart`, `dome` and `fiddlers-elbow` are Squarespace "Events List" pages sharing a `SquarespaceEventsGigsSource`, but `fiddlers-elbow` passes `descriptionFrom = ListingExcerpt`: it leaves every event page's body empty and writes the whole blurb into the listing's own excerpt, so its text comes from the listing and it makes no per-gig request at all. `the-garage` and `the-grace` are both DHP Family sites sharing identical card markup, so they share a `DhpVenueGigsSource` differing only in url/venue. `229`, `signature-brew-haggerston`, `signature-brew-blackhorse-road`, `blondies-taproom`, `blondies-bar`, `helgis` and `barfly` share a `DicePartnerVenueGigsSource`, which calls the Dice partner API (`partners-endpoint.dice.fm/api/v2/events`) that 229's own listing page drives its widget from, differing only in the venue it filters by. That filter matches the venue's *name*, not any id — passing the numeric id a dice.fm venue page carries returns an empty listing rather than an error — and the api key is the public widget one lifted from 229's page, which Dice does not scope to 229, so all seven venues stop listing at once if it is ever rotated. This is the one platform whose listing carries each gig's description inline (`raw_description`, the same copy the dice.fm event page shows, as against `description`, which appends Dice's own "Presented by ..." footer), so these venues make no per-gig request at all. Adding another only needs the venue's name as Dice spells it rather than as we do (`Blondies` for `blondies-bar`, `Barfly Camden` for `barfly`) — a name Dice doesn't use returns an empty listing rather than an error, exactly as a numeric id does. What that listing calls `perm_name` is not where a gig lives, though: dice.fm serves an event page under a perm_name prefixed with a short code of its own (`2wqb7p-its-never-over-...`) and answers the bare one with a 308 to it, and no Dice API hands the prefix out, so each gig's url is resolved through that redirect — one small request per gig, sent with a browser-like User-Agent because dice.fm answers anything else with a 403, and the reason these sources are handed a client that does *not* follow redirects. The dice.fm venue *pages* are read no more: they cap a listing at 30 gigs with a `load_more` flag set and no cursor to follow, which is why Haggerston (46 gigs) went through this API first, and they have since stopped carrying an event's perm_name at all, leaving nothing on them to identify a gig by. `windmill-brixton` is a Music Glue site: its cards print the date without a year, so the year is read off the front of each event's own path (`/events/2026-08-16-magnolia-...`), and its "Next" link stays in the markup on the last page pointing at `#` with `disabled` set, so pagination follows only an enabled one. Its posters come from a CDN that names them after the event with no file extension at all, which is why `imageUrlExtension` looks only at the last path segment. `islington-assembly-hall` prints no year on a card either, but has no per-event path to read one off, so the year is counted forward as the listing crosses back into an earlier month — the gigs stay in date order across its five pages, so that count carries across them rather than restarting. Its posters are lazy-loaded as an anchor's background, so a card carries `data-src` and no `src` at all; the url in it is a 750x450 crop named `<original>-750x450-c-center.<ext>`, and stripping that suffix recovers uploads measured up to 2560x1536. Every one of its event pages closes with the same two paragraphs — the ticket terms and the £1.50 Venue Levy, about 470 characters between them, and the whole description on a listing whose promoter wrote nothing — which are siblings of the real copy in one wysiwyg block and so are dropped by their wording, along with the age line. The "Presented by <promoter>" line is deliberately kept. `eventim-apollo` serves its whole listing in one page — the month bar above the cards filters what's already there rather than navigating — so it has nothing to paginate through and a size assertion in its test is what stands between that changing and a silently truncated listing. Its cards print a date two ways, "Thursday 20th August 2026" for a single day and "Aug 16th - Aug 23rd 2026" for a run of them, and a range writes the year only once, on the end date, so one crossing new year would date its start a year late — handled the same way as `alexandra-palace`, whose listing has the same habit. Each card carries two `<picture>` elements, one per breakpoint, and the narrow one is a generic house image rather than the gig's own on some listings, so the first is taken; its url already asks the CDN for 768 square, the size `render` targets, which is why this is the one source that doesn't rewrite the image url it's given. `ovo-arena` doesn't read its listing page at all: that page renders cards server-side but filters them in the browser, its query string is ignored, its cards carry no category of their own, and its "More Events" button pages twelve at a time through an endpoint the page never names. The calendar its month widget is driven from answers all of that — `/events/calendar/{year}/{month}` returns every event that month as JSON, each carrying the `Category` the "All Categories" drop-down filters on (Sports 1, Music 3, Comedy 4, Performance 5), and Music is what's kept. That means one request per month and so a fixed horizon rather than a followed one: eighteen months, because counting empty months would stop early — read on 2026-08-17 the calendar had nothing at all in January 2027 and three gigs in each of February and March. `indigo-at-the-o2` and `the-o2-arena` are the two rooms The O2 lists on its own site, sharing a `TheO2VenueGigsSource` that differs only in the site's own numeric id for each (indigo 2, the arena 1, as the listing page's own "Load More" button carries). That page renders only the first 24 events and arrives with its "Load More" button already disabled - the arena's page does the same and plainly has more, so the page alone reads as a whole listing when it is a quarter of one. The script behind that button calls `/events/events_ajax/{offset}?venue=<id>&...`, which is what the source walks instead, 24 at a time until a batch comes back empty; the `per_page` in that query is sent by the site itself but ignored by the server, so the offset in the path is the only way through. Each batch is one JSON string holding an html fragment, decoded the way New Cross Inn's is before being parsed. Their cards write a single date with its own year but a range with the year only on the end date, the same trap as `alexandra-palace` and `eventim-apollo`, and they abbreviate a month except where abbreviating saves nothing - the arena writes "June" and "July" in full while every other month is three letters, so both spellings are read. The arena's programme is far wider than indigo's - boxing, awards ceremonies, family shows - and the site's genre filter has no metal in it, only Rock, so everything is taken and left to the classifier as at `alexandra-palace`. Each card carries a 480x281 crop and a square one of at least 564px, and it's the square that's taken, being what survives render's own square crop. Two quirks: an event with no poster carries `"ImageURL": false` rather than a url or a null, which no Kondor string converter will take, so that field is read as a node and anything but a string is treated as no poster; and a run of nights is one event page listed once per night, so each gig's url gets its own date appended as a fragment (`.../detail/andre-rieu-16#2026-09-17`) to tell the nights apart, which also collapses an afternoon and an evening showing of the same thing on one date into the single gig the page wants.
- `classify [limit]` projects the current gigs from `events.ndjson` and, for any gig not yet classified, asks Claude Haiku (via `http4k-ai-llm-anthropic`) for a Metal/Other judgement at temperature 0, using the page text `scrape` captured (only fetching the page itself for a gig observed before that was recorded). Requires an `ANTHROPIC_API_KEY` environment variable (fails fast with a clear message if missing) and makes a real paid API call per gig, so the whole backlog is slow and worth chunking with the numeric `limit` (e.g. `classify 5` takes the next 5 soonest-upcoming unclassified gigs). Gigs already classified are skipped, including ones a user has overridden. When an event page's text is too thin to judge (under 80 chars) and the gig has a poster image, it falls back to sending that image to Claude Sonnet instead (which rejects a temperature override, so it runs at the API's own default). That image must be under ~7MB, since the API refuses anything whose base64 encoding tops 10MB — the size is checked locally before sending, so an oversized poster fails by name without costing a paid call. A gig that can't be judged (oversized poster, event page that won't load) fails on its own and does **not** abort the run: the successes are still appended and the failures are listed under "Could not classify N gig(s) - they stay Pending". This matters because classify appends only once, at the end — before it was made per-gig tolerant, a single failure late in a run discarded every paid call made before it. Such a gig stays `Pending` indefinitely and will fail the same way on every future run, so `classify override` is the only way to settle it. Prints a summary: how many gigs were classified this run with their Metal/Other split, what it cost, any failures, then the overall current-gigs breakdown (Metal/Other/Pending) across the whole log. The cost is exact rather than estimated — the Anthropic response reports the tokens it billed (`ChatResponse.metadata.usage`), and those counts are recorded on each `GigClassified` alongside the model, so a run's spend and any past run's can both be priced from the log. It's split by path because the two differ by much more than their per-token rates: a vision call also carries the poster's own image tokens, which the text path never pays for. Rates live in `llmRate` in `GigClassifier.kt` and are dated — Sonnet 5 is on introductory pricing until 2026-08-31, so that function takes the date the classification ran and prices it at the rate in force then. A classification with no recorded tokens (written before they were recorded, or a reply that arrived without usage) is reported as unpriced rather than as free.
- `classify status` reports what's been classified and what hasn't, and does nothing else — no API key, no network, no cost, nothing appended to the log. It prints the Metal/Other/Pending split twice, once over all current gigs and once over upcoming ones only, then a per-venue count of the upcoming `Pending`. The upcoming split is the one that matters for publishing, since only upcoming gigs block `render` — a backlog made up of gigs already in the past isn't what's standing in the way, and the per-venue breakdown usually points straight at a venue that's just been scraped for the first time. Use this rather than `render` when you only want to know where things stand: `render` reports upcoming gigs alone, refuses to do its actual job while any are unresolved, and lists at most 5 unless passed `full-unresolved`.
- `classify override <url> <metal|other>` is the manual counterpart to `classify` — same operation (both append a `GigClassified`), differing only in who decided. It records `source = User` for the gig with that url, asserting its genre directly and finally: it always wins regardless of what the classifier said or will say, and a later `classify` run skips that gig. No network calls, no API key needed. This is how you correct a verdict you disagree with. Note it must be passed as separate arguments (`"classify" "override" "<url>" "metal"`), not as one combined string — see the calling conventions above.
- `render [yyyy-mm-dd] [force] [full-unresolved]` first checks every current gig on or after the reference date (today by default, or the given `yyyy-mm-dd`) for being still `Pending`, sorted soonest-first. If any are found and `force` wasn't passed, it fails fast (writing nothing) with the count and, by default, just the soonest 5; each is listed as three lines: date/venue/title, then its status ("Pending (not yet classified)"), then its url. Pass `full-unresolved` to list all of them instead of just 5 (there is no standalone command for this — `render` without `force` doubles as the "what's left to classify" report, and is the only way to see the full list). Pass `force` to skip the check and render anyway. Once past the check (or with `force`), it keeps only the gigs settled as Metal (settled-`Other` gigs are excluded too) and excludes gigs before the reference date. Before writing `index.html` it makes `images/` hold exactly the images that page references, copying each out of `.image-cache/` and deleting any the page no longer uses (reported as "Unpublished N image(s)"). Pruning to just the rendered gigs is safe because the cache keeps the bytes — a later or backdated render republishes them with a local copy, so `render <past date>` pulls past gigs' images back and a normal render releases them again, with no network involved either way. If the cache somehow lacks an image (a gig scraped before the cache existed, or whose download failed) it's fetched then; a fetch that fails is reported per-gig and does **not** abort the render, since one dead url shouldn't stop every other gig being published. This is also why there's no separate prune command. The page itself is written to `.rendered/<yyyy-MM-dd'T'HH-mm-ss'Z'>.html` (gitignored, every render kept) and `index.html` is a copy of the most recent one — the same archive/published split as `.image-cache/` and `images/`. A successful render then appends a `GigsRendered` entry to `events.ndjson` naming that archived file, the gig count, and the `logicalDate` it rendered as of (the reference date above — today, or the `yyyy-mm-dd` given), which is what tells a backdated `render <past date>` apart from a normal one rather than leaving them to be guessed at from the gig count. `logicalDate` is deliberately distinct from `recordedAt`, the wall-clock time the entry was written. It's the one log entry that isn't about a single gig, so projections filter it out by type, and it's written only after both files land, so its presence always means a render that completed.
- `compact` rewrites `events.ndjson` keeping, per gig, only the latest `GigObserved` and only the one `GigClassified` that decides its genre — the user's override if there is one, the latest LLM verdict otherwise, which is exactly what `classificationStatus` picks. Not simply the newest classification: a `classify` run after an override records a fresh LLM verdict that must *not* win, and keeping only that would silently flip the gig's genre. Every `GigsRendered` entry is kept — they record what was published rather than what a gig is, and there's one per render rather than one per gig. This is the only command that destroys anything: the history of how a gig changed (gaining "- SOLD OUT", being rescheduled, having its page text captured) and which model made a since-superseded call are gone. It's also the only command that rewrites the log rather than appending to it, so don't run it while anything else might be appending. Nothing is overwritten until the compacted file has been written alongside, read back, and shown to project the same gigs, genres, classified set, scrape times and renders as the log it replaces; if any of those differ it fails having written nothing. `events.ndjson` is committed, so the swap is recoverable from git regardless. On the log as of 2026-08-15 it took 4035 entries (4.8MB) to 2653 (1.6MB), almost all of it duplicate `observed` entries carrying the same event page text again.
- `ingest-poster <imageUrl> <sourceUrl> <venue-id> [force]` is for a venue whose gigs are never scrapeable normally — e.g. a monthly calendar posted only as a single flyer image on social media, where there's no page of per-gig markup to parse. `venue-id` is a `VenueId` in `allVenues` (`Venue.kt`) and fails fast if it isn't one: such a venue has no `GigsSource`, so it isn't in the `scrape` list above, but it still has to be declared — `the-dev` is the one there today. It fetches `imageUrl` directly (not `sourceUrl` — that's never fetched, since e.g. Facebook blocks plain HTTP access to its pages outright; `imageUrl` needs to be the poster's own direct image link, obtained by the caller some other way, such as "copy image address" in a logged-in browser) and sends it to Claude Sonnet (vision) with a structured-extraction prompt asking for every gig's date and title. Every extracted gig gets `genre = Metal, source = User` immediately — there's no per-gig page text to classify against, so this assumes the whole poster is metal rather than leaving gigs `Pending` — and since there's no per-gig page to link to either, each gig's url is synthesized as `{sourceUrl}#gig-{slug(title)}-{date}`: a real, working link to the actual poster (sourceUrl), just not scrolled/highlighted to that one gig, since the source doesn't support that. Idempotent by default — skips (printing why) if any gig with this `sourceUrl`'s prefix is already in the log; pass `force` to re-run extraction anyway. Re-running is inherently a bit risky since the LLM re-reads the image fresh each time: if its wording of a title drifts slightly between runs, the derived url changes too, and it'll look like a new gig rather than an update — `force` should be used sparingly, not as a routine refresh.
