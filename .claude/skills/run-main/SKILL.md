---
name: run-main
description: Run the app's main entry point to scrape gigs, classify their genre, manually override a gig's genre, ingest a poster-only venue's gigs from an image, render the HTML page (which also reports unclassified gigs), or prune orphaned cached images. Use when asked to run the app, scrape gigs, classify gigs, list/review unclassified gigs, override/correct a gig's genre, ingest a gig poster image, clean up stale cached images, or render the gigs page.
---

Run `.claude/scripts/run-main.sh [scrape [venue-key...] [force]|classify [limit]|classify override <url> <metal|other>|render [yyyy-mm-dd] [force] [full-unresolved]|prune-images|ingest-poster <imageUrl> <sourceUrl> <venue> [force]]` from the project root using the Bash tool. There is no combined "do everything" mode and no default — running it with no arguments, or an unrecognised one, just prints the usage line. Chain the individual commands yourself when you want a full refresh (typically `scrape`, then `classify`, then `render`). Two calling conventions, and they behave differently — pick based on whether any argument needs a literal space in it:
  - **Separate arguments** (`.claude/scripts/run-main.sh "ingest-poster" "https://.../poster.jpg" "https://.../post" "The Dev"`, one Bash-tool string per logical argument): each argument's own spaces survive intact. Use this whenever an argument itself needs to contain a space, e.g. `ingest-poster`'s free-text `venue`, or a url that happens to have one.
  - **One combined string** (`.claude/scripts/run-main.sh "classify 5"`, `.claude/scripts/run-main.sh "render force"`): gets split into separate arguments on whitespace, so don't use this form for anything containing a value that must keep its spaces — e.g. `ingest-poster "https://.../poster.jpg" "https://.../post" "The Dev"` as one combined string would wrongly split "The Dev" into two arguments and miscount `ingest-poster`'s 3 required positional args.
  (Mechanically: the script encodes and joins separate arguments itself before handing them to `gradlew run --args=...`, since Gradle's `--args` value is otherwise re-split on any whitespace before Kotlin ever sees it, which is also why a single combined string works the same as before — Gradle does that splitting itself in that case.)

Genre is judged by a single LLM call per gig, at temperature 0 so verdicts are reproducible. A gig with a classification is `ClassificationStatus.Classified(genre)`; one the classifier hasn't reached yet is `Pending` and stays out of the rendered Metal page. A `source = User` override (via `classify override`) is always final and beats the classifier's verdict.

- `scrape [venue-key...] [force]` fetches gigs and appends a `GigObserved` entry per gig to `events.ndjson` (the append-only event log; never overwritten) — but first skips any venue scraped within the last day, printing "Skipping <venue> - scraped within the last day; pass force to scrape anyway" for each one and leaving it untouched. "Scraped within the last day" is approximated from the latest `GigObserved` per venue, not a dedicated scrape-event record, so a venue with no changes for longer than a day looks stale and gets rescraped anyway - that's the safe direction to be wrong in (scraped a bit more often than strictly necessary, never less). Pass `force` to bypass the cooldown and scrape every requested venue regardless. With no venue keys, considers all nineteen venues (skipping/scraping each per the cooldown); with one or more keys (e.g. `scrape dome underworld`), only those. Known keys: `cart-and-horses`, `new-cross-inn`, `our-black-heart`, `underworld`, `dome`, `blondies-taproom`, `blondies-bar`, `helgis`, `electric-ballroom`, `dingwalls`, `the-garage`, `roundhouse`, `signature-brew-blackhorse-road`, `signature-brew-haggerston`, `o2-forum-kentish-town`, `o2-academy-brixton`, `the-grace`, `o2-academy-islington`, `o2-shepherds-bush-empire`. An unknown key fails fast with the list of valid keys. The Academy Music Group venues (`o2-forum-kentish-town`, `o2-academy-brixton`, `o2-academy-islington`, `o2-shepherds-bush-empire`) have listing pages that render client-side and paginate in the browser, so unlike the other venues they don't scrape HTML at all — they call the JSON API those pages feed themselves from (`/api/search/events?VenueIds=<ids>&...`), with a `PageSize` well above the number of events actually listed so everything arrives in one request rather than needing to page through. Adding another AMG venue only needs its numeric id, which appears in each event's own `venue` object in that same API response (calling the API with no `VenueIds` at all returns every venue's events, which is the easy way to look one up). A venue can need more than one id: `o2-academy-islington` passes `4361,4258` because its listing covers both the main room and the smaller "Academy2" upstairs, which has no listing page of its own — both are recorded under the one venue name, exactly as the site presents them. Their gigs are identified by ticket-vendor url (mostly Ticketmaster, occasionally another vendor), and any event whose ticket sales have already closed comes back with no tickets at all — those are skipped with a printed note, since they'd have neither a stable identity nor a working link. `the-garage` and `the-grace` are both DHP Family sites sharing identical card markup, so they share a `DhpVenueGigsSource` differing only in url/venue. The two Signature Brew keys share one page (`events.signaturebrew.co.uk`) that lists both taprooms' gigs together, each tagged with its own venue name — each key fetches that same page independently and filters to its own venue, so scraping both in one run means two requests for identical content (a deliberate, minor tradeoff over adding a fetch-cache for one venue pair).
- `classify [limit]` projects the current gigs from `events.ndjson` and, for any gig not yet classified, fetches its event page and asks Claude Haiku (via `http4k-ai-llm-anthropic`) for a Metal/Other judgement at temperature 0. Requires an `ANTHROPIC_API_KEY` environment variable (fails fast with a clear message if missing) and makes a real paid API call per gig, so the whole backlog is slow and worth chunking with the numeric `limit` (e.g. `classify 5` takes the next 5 soonest-upcoming unclassified gigs). Gigs already classified are skipped, including ones a user has overridden. When an event page's text is too thin to judge (under 80 chars) and the gig has a poster image, it falls back to sending that image to Claude Sonnet instead (which rejects a temperature override, so it runs at the API's own default). Poster images are cached only for gigs classified Metal as a result of this run. Prints a summary: how many gigs were classified this run with their Metal/Other split, then the overall current-gigs breakdown (Metal/Other/Pending) across the whole log.
- `classify override <url> <metal|other>` is the manual counterpart to `classify` — same operation (both append a `GigClassified`), differing only in who decided. It records `source = User` for the gig with that url, asserting its genre directly and finally: it always wins regardless of what the classifier said or will say, and a later `classify` run skips that gig. No network calls, no API key needed. This is how you correct a verdict you disagree with. Note it must be passed as separate arguments (`"classify" "override" "<url>" "metal"`), not as one combined string — see the calling conventions above.
- `render [yyyy-mm-dd] [force] [full-unresolved]` first checks every current gig on or after the reference date (today by default, or the given `yyyy-mm-dd`) for being still `Pending`, sorted soonest-first. If any are found and `force` wasn't passed, it fails fast (writing nothing) with the count and, by default, just the soonest 5; each is listed as three lines: date/venue/title, then its status ("Pending (not yet classified)"), then its url. Pass `full-unresolved` to list all of them instead of just 5 (there is no standalone command for this — `render` without `force` doubles as the "what's left to classify" report, and is the only way to see the full list). Pass `force` to skip the check and render anyway. Once past the check (or with `force`), it keeps only the gigs settled as Metal (settled-`Other` gigs are excluded too) and excludes gigs before the reference date. It then downloads any poster image those gigs are missing before writing `index.html` — gigs are normally cached when first classified Metal, but anything removed since (by `prune-images` while the gig was classified otherwise, say) would otherwise leave a broken `<img>`, and here is the one place that knows exactly what's about to be published. Already-cached images are left alone, so this is usually a no-op and makes no requests. A download that fails is reported per-gig and does **not** abort the render: some image urls expire by design (Facebook CDN ones carry an expiry parameter), and one dead image shouldn't stop every other gig being published.
- `prune-images` deletes any file under `images/` that doesn't match a currently settled-Metal gig's expected filename (computed with the same `localImageFileName` hash used to write them) — e.g. leftovers from a gig later overridden away from Metal, or from before caching became Metal-only. Prints each removed filename and a trailing count. No network calls; safe to re-run (reports 0 removed once caught up). Note it deletes based on what is Metal *right now*, so pruning while gigs are unclassified removes images that are needed again once they're classified — `render` re-downloads those, so the two commands together keep `images/` correct in both directions.
- `ingest-poster <imageUrl> <sourceUrl> <venue> [force]` is for a venue whose gigs are never scrapeable normally — e.g. a monthly calendar posted only as a single flyer image on social media, where there's no page of per-gig markup to parse. It fetches `imageUrl` directly (not `sourceUrl` — that's never fetched, since e.g. Facebook blocks plain HTTP access to its pages outright; `imageUrl` needs to be the poster's own direct image link, obtained by the caller some other way, such as "copy image address" in a logged-in browser) and sends it to Claude Sonnet (vision) with a structured-extraction prompt asking for every gig's date and title. Every extracted gig gets `genre = Metal, source = User` immediately — there's no per-gig page text to classify against, so this assumes the whole poster is metal rather than leaving gigs `Pending` — and since there's no per-gig page to link to either, each gig's url is synthesized as `{sourceUrl}#gig-{slug(title)}-{date}`: a real, working link to the actual poster (sourceUrl), just not scrolled/highlighted to that one gig, since the source doesn't support that. Idempotent by default — skips (printing why) if any gig with this `sourceUrl`'s prefix is already in the log; pass `force` to re-run extraction anyway. Re-running is inherently a bit risky since the LLM re-reads the image fresh each time: if its wording of a title drifts slightly between runs, the derived url changes too, and it'll look like a new gig rather than an update — `force` should be used sparingly, not as a routine refresh.
