---
name: run-main
description: Run the app's main entry point to do the full daily update (scrape, classify, render), or any one step on its own - scrape gigs (including The Dev's, read off its monthly flyer by a local model), classify their genre, manually override a gig's genre, or render the HTML page (which also reports unclassified gigs and keeps the cached images in sync). Use when asked to run the app, do a daily/full update or refresh, scrape gigs, classify gigs, list/review unclassified gigs, override/correct a gig's genre, clean up stale cached images, or render the gigs page.
---

Run `.claude/scripts/run-main.sh [daily-update [force]|scrape [venue-id...] [force]|classify [limit]|classify status|classify override <url> <metal|other>|render [yyyy-mm-dd] [force] [full-unresolved]|compact]` from the project root using the Bash tool. There is no default — running it with no arguments, or an unrecognised one, just prints the usage line. For a full refresh use `daily-update` rather than chaining the three commands by hand. Two calling conventions, and they behave differently — pick based on whether any argument needs a literal space in it:
  - **Separate arguments** (`.claude/scripts/run-main.sh "classify" "override" "https://example.com/a gig" "metal"`, one Bash-tool string per logical argument): each argument's own spaces survive intact. Use this whenever an argument itself needs to contain a space, e.g. a url that happens to have one.
  - **One combined string** (`.claude/scripts/run-main.sh "classify 5"`, `.claude/scripts/run-main.sh "render force"`): gets split into separate arguments on whitespace, so don't use this form for anything containing a value that must keep its spaces — a url with a space in it would be split into two arguments, and the command would read the second half as another one.
  (Mechanically: the script encodes and joins separate arguments itself before handing them to `gradlew run --args=...`, since Gradle's `--args` value is otherwise re-split on any whitespace before Kotlin ever sees it, which is also why a single combined string works the same as before — Gradle does that splitting itself in that case.)

For a standalone build, `./gradlew shadowJar` produces `build/libs/metalgigs.jar` (~10MB, all dependencies inside), run as `java -jar build/libs/metalgigs.jar <same arguments>` — no encoding needed, arguments pass through normally, unlike `run-main.sh`. It must be run **from the project root**: every path the app touches (`events.ndjson`, `images/`, `index.html`, `.image-cache/`, `.rendered/`) is relative to the working directory, so the jar is self-contained in dependencies but not in data. It also needs a **Java 21** runtime, matching `jvmToolchain(21)`: on Java 26 the TLS handshake for venues whose sites omit their intermediate CA cert (e.g. The Garage) fails with `PKIX path building failed` even with `-Dcom.sun.security.enableAIAcaIssuers=true`, whereas on 21 it succeeds. `main()` sets that property itself, so the jar needs no `-D` flag of its own.

Scrape captures each gig's description from its own event page and stores it on the gig (`Gig.description`), so classifying later needs no network and can't be defeated by a page that has since changed or gone. It's blank only when the page was read and said nothing; one that couldn't be read fails its venue instead. The classifier never fetches an event page — any description under 80 characters, blank included, is judged from the poster. `newOrChangedGigs` compares the whole `Gig`, description included, so changed copy logs a fresh observation for every gig it changed: that is how the log dates a paragraph a venue has added, and equally why re-reading every gig's page minutes apart churns — one gig changed by a counter ticking over, eight flipped from empty to full on a flaky JS-rendered site.

Images live in two places. `.image-cache/` (gitignored) is a download cache keyed by image url, holding **every** scraped gig's image whatever its genre — it's filled during `scrape`, while the urls are still fresh, because some expire (the Facebook CDN ones carry an expiry parameter) and waiting until a gig is classified and rendered can be too late. Keying by url also means one poster shared by a month of gigs is stored once. `images/` (committed) holds only what the rendered page references, produced from the cache by `render`. That split is what makes `render` safe to prune: republishing reads the cache, never re-fetching against a url that may since have died.

Publishing **re-encodes rather than copies**, so `render` needs **ImageMagick** on the machine (`magick` on `PATH`, or `MAGICK_BINARY` pointing at it). Each image is resized so its *shorter* side is at most 768px — the side that survives the square `object-fit: cover` crop, and 2x the 260px the cards actually render at — then written as webp at quality 80, metadata stripped. Images already smaller than 768px are left at their own size rather than upscaled. This took the committed set from 175MB to 18MB with no visible change at card size. Two things to know: ImageMagick treats **quality 100 as *lossless* webp** (about 5.6x larger than 80), so that number is not a quality dial to nudge upward; and every published file is named `.webp` regardless of source format, with the name saying nothing about the size or quality used — so changing either in `ImageMagick.kt` will *not* re-encode what's already in `images/`. Delete the directory and re-render to force that, which costs no network because the cache still holds the originals. A conversion that fails is reported per-gig and doesn't abort the render. The same 768px conversion is reused when `classify` falls back to the poster image: Claude bills an image at `ceil(w/28) * ceil(h/28)` visual tokens, so sending a venue original (1667px at The Underworld, 4385px at the dice.fm venues) costs 3600-4784 tokens against 784 for the rendition the page already shows, for detail a genre judgement never uses. `DevGigSource` deliberately sends the full-size flyer, since it has to read a month of dates and titles off it rather than judge its artwork.

Genre is judged by a single LLM call per gig, at temperature 0 so verdicts are reproducible. A gig with a classification is `ClassificationStatus.Classified(genre)`; one the classifier hasn't reached yet is `Pending` and stays out of the rendered Metal page. A `source = User` override (via `classify override`) is always final and beats the classifier's verdict. Venues in `alwaysMetalVenues` (`Venue.kt`) never reach the LLM at all: `the-dev` books nothing but metal, and a gig read off its monthly flyer has no text to judge it by — its title is its whole description — so its genre is recorded as `Metal, source = User` without a call, which also means a forced reclassification leaves it alone.

- `daily-update [force]` runs `scrape`, then `classify`, then `render`, each printing under a `== step ==` header. It's the routine refresh, and the order is the only one that works: classifying can't judge gigs a scrape hasn't recorded yet, and rendering before classifying would leave them off the page. Each step calls the same function its own command does, so no step behaves differently from running the three by hand. What it adds is a `== venues ==` table between `classify` and `render`, one row per venue: what its listing held, how much of that was new or changed against what the log already had, how long it took, how many of its gigs were classified this run, and any problem reported for it. Only `daily-update` can print it - `scrape` doesn't know what will be classified and `classify` doesn't know what was listed - and it comes before `render` so a run that ends there still has it. The counts describe the listing rather than the log, so a venue whose gigs validation withheld still counts them and says "listing withheld" against itself. It runs **at most once a day**: if the log already holds a `GigsRendered` entry whose `logicalDate` is today it prints "Skipping - already updated for <date>; pass force to update anyway" and does nothing. The check is on `logicalDate`, not the newest render's timestamp, so a backdated `render <past date>` doesn't count as having done today, and today's counts however early in the day it happened. The log is the only state involved — nothing else tracks when the last update ran. `force` means "do it again anyway" and carries through to `scrape`, since that command's own per-venue cooldown would otherwise skip every venue and leave a forced run with nothing to do but re-render. It deliberately does **not** carry through to `render`, whose `force` means the unrelated "publish despite gigs nobody has classified" — never something a routine update should decide by itself; run `render force` yourself if that's what you want. Because each step persists as it goes (the log is append-only), a failure at `render` keeps everything `scrape` and `classify` just did — rerunning after settling those gigs costs only the render. Expect it to take a while: `classify` makes one paid API call per unclassified gig, so a run picking up a day's worth of new gigs can take several minutes, and one clearing a large backlog considerably longer.
- `scrape [venue-id...] [force]` fetches gigs and appends a `GigObserved` entry per gig to `events.ndjson` (the append-only event log; never overwritten), downloads every scraped gig's image into `.image-cache/`, and captures each gig's own event-page text onto the gig — but first skips any venue scraped within the last day, printing "Skipping <venue> - scraped within the last day; pass force to scrape anyway" for each one and leaving it untouched. Each venue it does scrape prints its position in the run ("Scraping The Grace (19/33)...") and how long it took, since a venue whose gigs each need their own event page fetched can be minutes of silence on its own. After validating what it read, it also asks what became of a still-upcoming gig the log holds that the venue has stopped listing, in the one run that can tell - by the next one it is simply a gig the listing doesn't carry, of which every venue has plenty. It asks only where there is an answer to be had: a gig listed that night whose title mostly matches the missing one's, or which carries the same poster, is what makes it worth one request to the old url. With nothing like it listed that night - a gig cancelled outright, most often - no request is made, since nothing could have paired with it anyway and a run that pairs nothing records nothing, so it would be asked again every day until its date passed. A venue that redirects that url to a gig now listed has said where the gig went; one that has deleted the page (404/410) leaves the gig on that night whose title shares most of its words to stand in for saying so, and a page still being served says the gig has not moved at all. Either way of moving appends a `GigReplaced` entry, which is what stops a venue swapping a support act (Cart and Horses and dice.fm both build a url out of the title) from publishing one night as two cards: `currentGigs` leaves out a url that has been replaced, and `classificationStatus` reads the new url's genre from the old one, so the move costs neither a duplicate nor a paid call. Skipped for a venue whose gigs validation withheld, since a listing that failed a check is not one to conclude anything from. "Scraped within the last day" is approximated from the latest `GigObserved` per venue, not a dedicated scrape-event record, so a venue with no changes for longer than a day looks stale and gets rescraped anyway - that's the safe direction to be wrong in (scraped a bit more often than strictly necessary, never less). Pass `force` to bypass the cooldown and scrape every requested venue regardless. With no venue ids, considers all thirty-five venues (skipping/scraping each per the cooldown); with one or more ids (e.g. `scrape dome underworld`), only those. - `classify [limit]` projects the current gigs from `events.ndjson` and, for any gig not yet classified, asks Claude Haiku (via `http4k-ai-llm-anthropic`) for a Metal/Other judgement at temperature 0, using the page text `scrape` captured. Requires `ANTHROPIC_API_KEY`, which `run-main.sh` reads from `~/.metalgigs.env` (mode 600, the same file the launchd agent relies on) when the environment doesn't already carry it — so nothing has to be exported or sourced first, and in particular never `source ~/.zshrc` to get it, which a non-interactive shell doesn't read anyway. Missing from both, it fails fast with a clear message, before any paid call. It makes a real paid API call per gig, so the whole backlog is slow and worth chunking with the numeric `limit` (e.g. `classify 5` takes the next 5 soonest-upcoming unclassified gigs). Gigs already classified are skipped, including ones a user has overridden. When an event page's text is too thin to judge (under 80 chars) and the gig has a poster image, it falls back to sending that image to Claude Sonnet instead (which rejects a temperature override, so it runs at the API's own default). That image must be under ~7MB, since the API refuses anything whose base64 encoding tops 10MB — the size is checked locally before sending, so an oversized poster fails by name without costing a paid call. A gig that can't be judged (oversized poster, event page that won't load) fails on its own and does **not** abort the run: the successes are still appended and the failures are listed under "Could not classify N gig(s) - they stay Pending". This matters because classify appends only once, at the end — before it was made per-gig tolerant, a single failure late in a run discarded every paid call made before it. Such a gig stays `Pending` indefinitely and will fail the same way on every future run, so `classify override` is the only way to settle it. Prints a summary: how many gigs were classified this run with their Metal/Other split, what it cost, any failures, then the overall current-gigs breakdown (Metal/Other/Pending) across the whole log. The cost is exact rather than estimated — the Anthropic response reports the tokens it billed (`ChatResponse.metadata.usage`), and those counts are recorded on each `GigClassified` alongside the model, so a run's spend and any past run's can both be priced from the log. It's split by path because the two differ by much more than their per-token rates: a vision call also carries the poster's own image tokens, which the text path never pays for. Rates live in `llmRate` in `GigClassifier.kt` and are dated — Sonnet 5 is on introductory pricing until 2026-08-31, so that function takes the date the classification ran and prices it at the rate in force then. A classification with no recorded tokens (written before they were recorded, or a reply that arrived without usage) is reported as unpriced rather than as free.
- `classify status` reports what's been classified and what hasn't, and does nothing else — no API key, no network, no cost, nothing appended to the log. It prints the Metal/Other/Pending split twice, once over all current gigs and once over upcoming ones only, then a per-venue count of the upcoming `Pending`. The upcoming split is the one that matters for publishing, since only upcoming gigs block `render` — a backlog made up of gigs already in the past isn't what's standing in the way, and the per-venue breakdown usually points straight at a venue that's just been scraped for the first time. Use this rather than `render` when you only want to know where things stand: `render` reports upcoming gigs alone, refuses to do its actual job while any are unresolved, and lists at most 5 unless passed `full-unresolved`.
- `classify override <url> <metal|other>` is the manual counterpart to `classify` — same operation (both append a `GigClassified`), differing only in who decided. It records `source = User` for the gig with that url, asserting its genre directly and finally: it always wins regardless of what the classifier said or will say, and a later `classify` run skips that gig. No network calls, no API key needed. This is how you correct a verdict you disagree with. Note it must be passed as separate arguments (`"classify" "override" "<url>" "metal"`), not as one combined string — see the calling conventions above.
- `render [yyyy-mm-dd] [force] [full-unresolved]` first checks every current gig on or after the reference date (today by default, or the given `yyyy-mm-dd`) for being still `Pending`, sorted soonest-first. If any are found and `force` wasn't passed, it fails fast (writing nothing) with the count and, by default, just the soonest 5; each is listed as three lines: date/venue/title, then its status ("Pending (not yet classified)"), then its url. Pass `full-unresolved` to list all of them instead of just 5 (there is no standalone command for this — `render` without `force` doubles as the "what's left to classify" report, and is the only way to see the full list). Pass `force` to skip the check and render anyway. Once past the check (or with `force`), it keeps only the gigs settled as Metal (settled-`Other` gigs are excluded too) and excludes gigs before the reference date. Before writing `index.html` it makes `images/` hold exactly the images that page references, copying each out of `.image-cache/` and deleting any the page no longer uses (reported as "Unpublished N image(s)"). Pruning to just the rendered gigs is safe because the cache keeps the bytes — a later or backdated render republishes them with a local copy, so `render <past date>` pulls past gigs' images back and a normal render releases them again, with no network involved either way. If the cache somehow lacks an image (a gig scraped before the cache existed, or whose download failed) it's fetched then; a fetch that fails is reported per-gig and does **not** abort the render, since one dead url shouldn't stop every other gig being published. This is also why there's no separate prune command. The page itself is written to `.rendered/<yyyy-MM-dd'T'HH-mm-ss'Z'>.html` (gitignored, every render kept) and `index.html` is a copy of the most recent one — the same archive/published split as `.image-cache/` and `images/`. A successful render then appends a `GigsRendered` entry to `events.ndjson` naming that archived file, the gig count, and the `logicalDate` it rendered as of (the reference date above — today, or the `yyyy-mm-dd` given), which is what tells a backdated `render <past date>` apart from a normal one rather than leaving them to be guessed at from the gig count. `logicalDate` is deliberately distinct from `recordedAt`, the wall-clock time the entry was written. It's the one log entry that isn't about a single gig, so projections filter it out by type, and it's written only after both files land, so its presence always means a render that completed.
- `compact` rewrites `events.ndjson` keeping, per gig, only the latest `GigObserved` and only the one `GigClassified` that decides its genre — the user's override if there is one, the latest LLM verdict otherwise, which is exactly what `classificationStatus` picks. Not simply the newest classification: a `classify` run after an override records a fresh LLM verdict that must *not* win, and keeping only that would silently flip the gig's genre. Every `GigsRendered` entry is kept — they record what was published rather than what a gig is, and there's one per render rather than one per gig. This is the only command that destroys anything: the history of how a gig changed (gaining "- SOLD OUT", being rescheduled, having its page text captured) and which model made a since-superseded call are gone. It's also the only command that rewrites the log rather than appending to it, so don't run it while anything else might be appending. Nothing is overwritten until the compacted file has been written alongside, read back, and shown to project the same gigs, genres, classified set, scrape times and renders as the log it replaces; if any of those differ it fails having written nothing. `events.ndjson` is committed, so the swap is recoverable from git regardless. On the log as of 2026-08-15 it took 4035 entries (4.8MB) to 2653 (1.6MB), almost all of it duplicate `observed` entries carrying the same event page text again.
