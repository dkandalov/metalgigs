---
name: run-main
description: Run the app's main entry point to scrape gigs, classify their genre, manually override a gig's genre, ingest a poster-only venue's gigs from an image, render the HTML page (which also reports unresolved gigs), prune orphaned cached images, or all of scrape+classify+render. Use when asked to run the app, scrape gigs, classify gigs, list/review unresolved gigs, override/correct a gig's genre, ingest a gig poster image, clean up stale cached images, or render the gigs page.
---

Run `.claude/scripts/run-main.sh [scrape [venue-key...] [force]|classify [limit]|override <url> <metal|other>|render [yyyy-mm-dd] [force] [full-unresolved]|prune-images|ingest-poster <imageUrl> <sourceUrl> <venue> [force]|all]` from the project root using the Bash tool. Two calling conventions, and they behave differently — pick based on whether any argument needs a literal space in it:
  - **Separate arguments** (`.claude/scripts/run-main.sh "ingest-poster" "https://.../poster.jpg" "https://.../post" "The Dev"`, one Bash-tool string per logical argument): each argument's own spaces survive intact. Use this whenever an argument itself needs to contain a space, e.g. `ingest-poster`'s free-text `venue`, or a url that happens to have one.
  - **One combined string** (`.claude/scripts/run-main.sh "classify 5"`, `.claude/scripts/run-main.sh "render force"`): gets split into separate arguments on whitespace, so don't use this form for anything containing a value that must keep its spaces — e.g. `ingest-poster "https://.../poster.jpg" "https://.../post" "The Dev"` as one combined string would wrongly split "The Dev" into two arguments and miscount `ingest-poster`'s 3 required positional args.
  (Mechanically: the script encodes and joins separate arguments itself before handing them to `gradlew run --args=...`, since Gradle's `--args` value is otherwise re-split on any whitespace before Kotlin ever sees it, which is also why a single combined string works the same as before — Gradle does that splitting itself in that case.)

A gig only counts as classified once its Keywords and LLM classifications agree (a `ClassificationStatus.Classified(genre)`); if they disagree it's `Disputed`, and if only one of them has run yet it's `Pending` — both stay out of the rendered Metal page until resolved. A `source = User` override (via `override`) is always final regardless of what Keywords/LLM said or whether both have even run.

- `scrape [venue-key...] [force]` fetches gigs and appends a `GigObserved` entry per gig to `events.ndjson` (the append-only event log; never overwritten) — but first skips any venue scraped within the last day, printing "Skipping <venue> - scraped within the last day; pass force to scrape anyway" for each one and leaving it untouched. "Scraped within the last day" is approximated from the latest `GigObserved` per venue, not a dedicated scrape-event record, so a venue with no changes for longer than a day looks stale and gets rescraped anyway - that's the safe direction to be wrong in (scraped a bit more often than strictly necessary, never less). Pass `force` to bypass the cooldown and scrape every requested venue regardless. With no venue keys, considers all fifteen venues (skipping/scraping each per the cooldown); with one or more keys (e.g. `scrape dome underworld`), only those. Known keys: `cart-and-horses`, `new-cross-inn`, `our-black-heart`, `underworld`, `dome`, `blondies-taproom`, `blondies-bar`, `helgis`, `electric-ballroom`, `dingwalls`, `the-garage`, `roundhouse`, `signature-brew-blackhorse-road`, `signature-brew-haggerston`, `o2-forum-kentish-town`. An unknown key fails fast with the list of valid keys. `o2-forum-kentish-town` is the one venue that needs **Google Chrome installed locally** — its page is a JS-rendered SPA whose static HTML contains no event data, so it's scraped via headless Chrome (`ChromeHeadless`, which shells out to the browser binary) rather than a plain HTTP client. Chrome is found at the default macOS path or via a `CHROME_BINARY` env var, and fails fast with a clear message if missing. This affects only this venue: scraping any other venue individually needs nothing new, and `classify`/`render`/`override`/`prune-images`/`ingest-poster` are unaffected — but a no-venue-keys `scrape` (and therefore `all`) includes it, so those need Chrome too. It's also noticeably slower than every other venue (~15-20s, since a real browser has to render the page). The two Signature Brew keys share one page (`events.signaturebrew.co.uk`) that lists both taprooms' gigs together, each tagged with its own venue name — each key fetches that same page independently and filters to its own venue, so scraping both in one run means two requests for identical content (a deliberate, minor tradeoff over adding a fetch-cache for one venue pair).
- `classify [limit]` projects the current gigs from `events.ndjson` and always runs both classifiers: for any gig its Keywords classifier hasn't classified yet, fetches the event page and matches keywords against the page text (`source = Keywords`, `matchedKeywords` populated); independently, for any gig its LLM classifier hasn't classified yet, sends the title and page text to Claude Haiku via `http4k-ai-llm-anthropic` for a Metal/Other judgement (`source = LLM`, no `matchedKeywords`, non-deterministic). Each gig's two passes are tracked independently — a gig already classified by Keywords but not LLM only gets the LLM pass this run, and vice versa; a `source = User` override on a gig counts as settled for both passes and is skipped by both. Requires an `ANTHROPIC_API_KEY` environment variable (fails fast with a clear message if missing) and makes a real paid API call per not-yet-LLM-classified gig. With a numeric `limit` (e.g. `classify 5`), each pass independently classifies at most the next N soonest-upcoming gigs it hasn't touched yet — useful for bounding cost/time. Poster images are cached only for gigs that reach Metal consensus as a result of the current run. Prints a summary: how many gigs each pass classified this run (with a Metal/Other split), how many reached Metal consensus, how many newly disagree (Disputed), and then the overall current-gigs breakdown by status (Metal/Other/Pending/Disputed) across the whole log, not just this run.
- `override <url> <metal|other>` appends a `GigClassified` entry with `source = User` for the gig with that url, asserting its genre directly and finally — it always wins regardless of what Keywords/LLM said or will say, and a later `classify` run skips it entirely (both passes). No network calls.
- `render [yyyy-mm-dd] [force] [full-unresolved]` first checks every current gig on or after the reference date (today by default, or the given `yyyy-mm-dd`) for unresolved classification — never-classified, `Pending`, or `Disputed` — sorted soonest-first. If any are found and `force` wasn't passed, it fails fast (writing nothing) with the count and, by default, just the soonest 5 (date, venue, title, url per gig); pass `full-unresolved` to list all of them instead of just 5 (there is no standalone command for this anymore — `render` without `force` doubles as the "what's left to classify" report, and it's the only way to see the full list). Pass `force` to skip the check and render anyway. Once past the check (or with `force`), it projects the current gigs, keeps only the ones confirmed Metal by consensus (agreed-`Other` gigs are also excluded — there's no way to render them), excludes gigs before the reference date, and writes `index.html` (no network calls). Only consensus-Metal gigs are guaranteed to have a cached poster image (see `classify`/`override`), so this filtering isn't optional — anything else would risk broken `<img>` tags. `all` calls `render` without `force`, so it fails the same way if an upcoming gig is still unresolved after `classify` runs — this is deliberate (see `all` below).
- `prune-images` deletes any file under `images/` that doesn't match a currently consensus-Metal gig's expected filename (computed with the same `localImageFileName` hash used to write them) — e.g. leftovers from a gig that lost Metal consensus (reclassified, disputed), or from before caching became Metal-only. Prints each removed filename and a trailing count. No network calls; safe to re-run (reports 0 removed once caught up).
- `ingest-poster <imageUrl> <sourceUrl> <venue> [force]` is for a venue whose gigs are never scrapeable normally — e.g. a monthly calendar posted only as a single flyer image on social media, where there's no page of per-gig markup to parse. It fetches `imageUrl` directly (not `sourceUrl` — that's never fetched, since e.g. Facebook blocks plain HTTP access to its pages outright; `imageUrl` needs to be the poster's own direct image link, obtained by the caller some other way, such as "copy image address" in a logged-in browser) and sends it to Claude Sonnet (vision) with a structured-extraction prompt asking for every gig's date and title. Every extracted gig gets `genre = Metal, source = User` immediately — there's no page text to run Keywords/LLM classification against, so this assumes the whole poster is metal rather than leaving gigs `Pending` — and since there's no per-gig page to link to either, each gig's url is synthesized as `{sourceUrl}#gig-{slug(title)}-{date}`: a real, working link to the actual poster (sourceUrl), just not scrolled/highlighted to that one gig, since the source doesn't support that. Idempotent by default — skips (printing why) if any gig with this `sourceUrl`'s prefix is already in the log; pass `force` to re-run extraction anyway. Re-running is inherently a bit risky since the LLM re-reads the image fresh each time: if its wording of a title drifts slightly between runs, the derived url changes too, and it'll look like a new gig rather than an update — `force` should be used sparingly, not as a routine refresh.
- `all` (also the default when no argument is given) runs `scrape`, then `classify`, then `render` — it does not include `unclassified`, `override`, or `prune-images`, which are standalone. `scrape` here is not forced either, so running `all` again soon after skips any venue already scraped within the last day rather than re-hitting it. Since `classify` now always needs `ANTHROPIC_API_KEY`, so does `all`. `render` here is not forced, so if any upcoming gig is still `Pending`/`Disputed` after `classify` runs (e.g. a genuine Keywords/LLM disagreement, which `classify` can't resolve on its own), `all` fails at the render step rather than silently publishing a page with a gap — resolve it with `override` (or the `classify-unclassified-gigs` skill) and re-run.

Report what was produced and surface any errors from the Gradle output.
